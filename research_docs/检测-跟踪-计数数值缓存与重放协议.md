# 检测—跟踪—计数数值缓存与重放协议

> 建立日期：2026-07-25
> 协议性质：与具体计数优化方案解耦的工程加速、可复现和公平对比协议。
> 当前计数基准：2304×1296 参考画面，圆心 `(1185, 732)`，半径 `R=215 px`。

## 1. 目的与边界

本协议替代已经删除的、绑定 B0/E1/E2/E3 消融结构的旧缓存重放文档。恢复的是“逐级数值缓存与重放能力”，不是旧消融方案。

处理链路固定拆成三层：

```text
原始视频
  └─ 统一全帧检测器 ─> 逐帧检测缓存 D（完整画面坐标）
                         └─ 跟踪器 ─> 逐帧轨迹缓存 T
                                         └─ 计数器 ─> 事件与最终计数 C
```

这样可以按改动所在层选择最靠后的有效缓存：

| 改动内容 | 必须重新运行 | 可复用 |
|---|---|---|
| 权重、输入尺寸、检测区域、检测阈值、NMS、类别过滤 | 检测 + 跟踪 + 计数 | 原始视频 |
| 跟踪器、关联代价、阈值、轨迹生命周期 | 跟踪 + 计数 | 检测缓存 D |
| 圆心、半径、计数点、跨界逻辑、类别锁定、初始数量 | 仅计数 | 轨迹缓存 T |
| 可视化、CSV 排版 | 仅结果导出 | 对应数值缓存 |

因此，后续大多数跟踪优化不再重复 YOLO 推理，大多数计数优化不再重复 YOLO 和 MOT。缓存只能加速后处理研究，不能用来测试它上游已经改变的模块。

## 2. 当前文件与入口

- `benchmark_common/numeric_cache.py`：三层共用的缓存格式、原子写入、完整性与指纹校验；
- `detection_model_benchmark/cache_detections.py`：执行统一全帧检测并生成检测缓存，不绑定任何跟踪器；
- `counting_model_benchmark/replay_counting.py`：从轨迹缓存纯数值重放统一圆计数；
- `counting_model_benchmark/counting_core.py`：所有跟踪算法共用的计数圆和计数规则；
- `tracking_model_benchmark/01_sort...08_botsort/`：8 个候选跟踪算法的独立官方工作区；
- `tracking_model_benchmark/_common/tracker_interface.py`：统一 `Nx6 → Nx8` 跟踪器契约；
- `tracking_model_benchmark/_common/tracker_adapters.py`：8 个官方实现的内部输入输出适配；
- `tracking_model_benchmark/_common/run_tracker.py`：单算法检测缓存重放入口；
- `counting_model_benchmark/run_counting_benchmark.py`：8 算法统一轨迹与计数批处理入口；
- `counting_model_benchmark/evaluate_counting.py`：逻辑长视频分类计数指标汇总；
- `counting_model_benchmark/configs/`：版本化计数配置；
- `counting_model_benchmark/ablations/`：后续单因素计数消融定义；
- `counting_model_benchmark/tests/`：计数核心、缓存与重放行为的自动回归测试。

默认缓存目录是 `<output>/numeric_cache/`。文件名为：

```text
<video_stem>.detections.jsonl
<video_stem>.tracks.jsonl
```

目录输入会递归扫描，缓存树保留视频相对于 `--source` 的父目录结构；因此不同逻辑视频目录中允许出现相同的文件主名而不会互相覆盖。同一逻辑长视频内的物理片段主名仍必须唯一，并应使用可按真实时间顺序排序的编号。计数时只把同一逻辑长视频目录内的片段连续重放。

## 3. 通用格式

缓存使用 UTF-8 JSON Lines。它既能逐行流式读取，也能保存必要元数据；帧数据部分只包含数值数组，不保存图像。

每个文件由三部分组成：

1. 第一行 `header`：格式版本、类型、字段、视频和算法配置；
2. 中间每帧一行：帧号及该帧的数值行；
3. 最后一行 `footer`：缓存 ID、实际写出帧数和完整标志。

必须记录所有解码成功的帧。没有目标的帧也要写成空数组，禁止直接跳过，否则跟踪器的时间状态会改变。

### 3.1 检测缓存 D

每个检测行字段顺序固定为：

```text
[x1, y1, x2, y2, confidence, class_id]
```

帧记录示例：

```json
{"f":125,"d":[[1160.2,700.4,1194.8,739.1,0.873,1]]}
```

首轮 baseline 统一对完整画面执行检测，结果直接使用原视频的完整画面 `xyxy` 坐标。当前不使用 ROI；ROI 的形状、范围和是否启用属于后续计数优化变量，不混入 8 跟踪器首轮 baseline。

### 3.2 轨迹缓存 T

每个轨迹行字段顺序固定为：

```text
[x1, y1, x2, y2, track_id, confidence, class_id, detection_index]
```

帧记录示例：

```json
{"f":125,"t":[[1161.0,701.0,1195.1,739.8,17,0.873,1,0]]}
```

不能只保存中心点。保留完整框后，后续仍可比较框中心、底边中心、面积约束或其他计数点定义。`detection_index` 表示轨迹输出所对应的该帧检测索引；无法提供时记 `-1`。

## 4. 元数据和可追溯性

检测缓存头至少记录：

- 视频绝对路径、字节大小、修改时间；
- 画面宽高、FPS、解码器报告帧数；
- 完整画面坐标约定；
- 类别 ID 与名称映射；
- 权重文件信息、推理尺寸、置信度、IoU、精度模式和类别过滤；
- 检测区域（当前固定为完整画面）及完整画面坐标约定。

轨迹缓存头还必须记录：

- 上游检测缓存 ID；
- 跟踪器名称、参数和帧率；
- 该跟踪器是否依赖图像、ReID 特征或其他外观输入。

当前 `cache_id` 是规范化头信息的 SHA-256，用来判断配置链是否相同；视频字段当前使用路径、大小和修改时间作为快速文件签名。正式论文实验还应把冻结清单中的视频内容 SHA-256、权重内容 SHA-256、代码版本或提交号与结果一起归档，不能把快速签名误写成视频内容哈希。

## 5. 写入与读取约束

- 写入先落到隐藏临时文件，只有成功写完 footer 并 `fsync` 后才原子替换正式文件；
- 异常中断产生的临时文件不得重放；
- 读取时校验缓存版本、类型、头指纹、头尾缓存 ID、实际帧数、字段列数；
- 帧号必须从 1 开始严格连续；
- footer 后不得存在额外数据；
- 类别 ID 映射发生冲突时拒绝把多个轨迹缓存连续计数；
- OpenCV 报告的总帧数只作诊断，实际完整性以成功解码并连续写出的帧数和 footer 为准。

任何校验失败都应重新生成该层缓存，不能人工删行或强行继续。

## 6. 重放规则

### 6.1 跟踪重放

当前候选集固定为 SORT、ByteTrack、OC-SORT、SF-SORT、FastTracker、BoostTrack、HybridSORT 和 BoT-SORT。根目录不再提供绑定 ByteTrack 的跟踪入口；正式统一入口位于 `tracking_model_benchmark/_common/`。若 ByteTrack 最终最优，正式实现以 `tracking_model_benchmark/02_bytetrack/` 为准，不使用已删除的旧根目录 BoxMOT ByteTrack 适配代码。

统一公开契约固定为：

```text
输入 D：Nx6 [x1,y1,x2,y2,confidence,class_id]
输出 T：Nx8 [x1,y1,x2,y2,track_id,confidence,class_id,detection_index]
```

8 个算法的 `Nx5`、`boxes/scores`、Results-like 对象和占位图像等差异全部封装在 `tracker_adapters.py` 内。计数器不得导入任何算法源码。适配器直接传入完整画面检测框，并输出完整画面轨迹。类别与置信度统一取当前匹配检测；当前帧没有匹配时沿用该 ID 上一次观测值，这只是元数据传递，不是类别投票。

每个算法的适配器必须：

1. 按检测缓存的连续帧号逐帧调用跟踪器，空检测帧也必须推进一次；
2. 将输出转换为统一八列轨迹格式；
3. 在轨迹缓存头中记录算法目录、代码版本、全部参数和上游检测缓存 ID；
4. 每个物理片段独立初始化；
5. 将不同算法的轨迹缓存写到彼此隔离的结果目录。

如果后续比较的算法需要 ReID、分割掩膜或原始图像纹理，仅有六列检测缓存不够。此时必须选择以下一种方式并在元数据中注明：

1. 读取原视频帧；
2. 预先缓存由冻结外观模型生成的 embedding；
3. 扩展独立的 mask/feature 缓存格式。

不得给需要外观信息的方法填充伪特征后，再声称是公平的完整算法对比。

### 6.2 计数重放

`counting_model_benchmark/replay_counting.py` 对每个物理片段重置 `track_id → 圆内外状态` 和类别状态；同一输入目录内的有符号区域计数持续累计，以表示同一个逻辑长视频。8 个算法必须分别调用同一计数入口，禁止在各算法工程中复制并修改计数规则。

当前默认规则是：

- 轨迹框中心从圈外到圈内：`+1`；
- 从圈内到圈外：`-1`；
- ID 首次出现时只建立状态，不产生事件；
- 不做 B0/E1/E2/E3、轨迹拼接、类别投票、时序确认或负数截断；
- 默认参考圆为 `(1185,732), R=215`，其他分辨率按 `counting_model_benchmark/counting_core.py` 的同一规则缩放。

## 7. 使用命令

### 7.1 视频处理并生成统一检测缓存

```bash
python detection_model_benchmark/cache_detections.py \
  --source video_data \
  --weights <best.pt> \
  --output project_results/detection_cache/<detector_run_id> \
  --conf 0.10
```

`cache_detections.py` 只生成 `*.detections.jsonl`、`detection_cache_summary.csv` 和 `run_config.csv`。上述目录命令递归处理全部视频，并形成 `numeric_cache/<逻辑长视频目录>/<物理片段>.detections.jsonl` 的保序结构。检测专用 baseline 的 YOLO predict 默认阈值仍是 `0.25`；但 8 跟踪器的 detection-only baseline 使用 `conf=0.10` 作为共享缓存下限，使原生低分框分支或检测分数增强不会在缓存阶段被提前截断。`0.10` 不是 8 个算法统一的跟踪阈值：ByteTrack、OC-SORT、SF-SORT、FastTracker、BoostTrack、HybridSORT 和 BoT-SORT 使用各自官方默认阈值；SORT 原生没有置信度过滤，因此不额外增加人为阈值。任一受控对比中 8 个跟踪器必须读取完全相同的检测缓存。可用 `--numeric-cache-dir <目录>` 改变检测缓存位置。

### 7.2 运行 8 个候选跟踪器

在独立 `bench_tracking` 环境中运行全部 8 个候选及同一计数器：

```bash
python counting_model_benchmark/run_counting_benchmark.py \
  --detections project_results/detection_cache/<detector_run_id>/numeric_cache \
  --output project_results/counting_model_benchmark/<counting_run_id> \
  --counting-config counting_model_benchmark/configs/baseline_circle_v1.json
```

只运行单个跟踪器时使用：

```bash
python tracking_model_benchmark/_common/run_tracker.py \
  --tracker ocsort \
  --detections project_results/<检测缓存根目录> \
  --output project_results/<OCSORT轨迹目录> \
  --config tracking_model_benchmark/03_ocsort/configs/counting_candidate_v1.json
```

每个跟踪器的 `counting_candidate_v1.json` 是面向纯检测数值输入的官方默认 baseline 起点。SORT、ByteTrack、OC-SORT、SF-SORT、FastTracker 和 BoT-SORT 采用官方构造器、主评测入口或已注册 YAML 的默认参数；BoostTrack 采用默认 MOT17 分数参数；HybridSORT 采用官方 canonical MOT17 no-ReID 实验参数。不能由缓存提供的 ReID、外观嵌入、GMC/ECC 等图像功能关闭，这是相对完整图像输入版本唯一必要的约束，不属于验证集调参。上述配置不是已在实蝇验证集上求得的最优参数，也尚未冻结为正式结果参数。计数规则独立使用 `counting_model_benchmark/configs/baseline_circle_v1.json`；重放结果会记录解析后的计数配置指纹。后续微调应新建版本化配置和 `counting_run_id`，不得覆盖已报告的官方默认 baseline。

### 7.3 从轨迹缓存快速重跑计数

```bash
python counting_model_benchmark/replay_counting.py \
  --tracks project_results/<八算法计数实验>/<算法名>/tracks/<逻辑长视频目录> \
  --output project_results/<算法名>/counting
```

测试其他圆时可以传入 `--center-x`、`--center-y`、`--radius`；若逻辑长视频开始时瓶内已有目标，可按类别重复指定 `--initial-count 0=2`。

六个逻辑长视频全部完成后，可生成诊断指标：

```bash
python counting_model_benchmark/evaluate_counting.py \
  --results project_results/<八算法计数实验>
```

## 8. 正式实验管理

每个候选方法至少保存：

- 输入检测缓存 ID 集合；
- 输出轨迹缓存 ID 集合；
- 计数配置与结果 CSV；
- 参数配置、代码版本、运行时间和运行环境；
- 所属 development/validation/test 划分。

同一 MOT 对比必须使用同一组检测缓存；同一计数方法对比必须使用同一组轨迹缓存。验证集可以重放调参，测试集应在方法和参数冻结后运行。数值重放能保证输入一致并显著加速实验，但不能代替人工真值、标准 MOT 标注或正式精度评价。
